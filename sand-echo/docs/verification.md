### 2.1 脚本编译门禁（`tests/script_compile.gd`）

**这一项是补进来的**，因为踩过一个具体的坑：`godot --headless --import` **只导入资源、不编译 `.gd`**，所以脚本解析错误会被静默跳过。当时把 `game.gd` / `shop.gd` 改到加载失败，却因为 `--import` 报「无错误」就以为解析通过，直到 `wave_smoke` 报「竞技场未生成」「商店面板缺失」才暴露—— 脚本没编译，节点根本没建。

门禁逐个 `load()` 全部 39 个脚本。**注意不能只判 `load()` 是否为 null**：实测 Godot 4.6 在脚本解析失败时**仍返回非 null 的 GDScript 对象**（处于错误态），判 null 会漏掉，所以必须再用 `can_instantiate()`。

它当场抓到了一个真实失效条目：`tests/memory_test.gd` 引用已删除的 `Dungeon` 类型，**编译都不过**，此前一直没人发现。

当前状态：**39 个脚本全部编译通过**（含本轮新增的 `tests/screenshot.gd` 与 `tools/pck_probe.gd`）。

## 6. 手感与可辨性

### 6.1 暂停与顿帧（`tests/feel_audit.gd`，24 项断言）

全部通过。

**ESC 无法暂停曾是三层同坏**：无 `_unhandled_input`；调用的 `toggle()` 不存在；从不设 `get_tree().paused`。且 Game 为 `PAUSABLE`，把自己 pause 后收不到输入 —— 解除暂停改由 `PauseMenu`（`process_mode = 3` / ALWAYS）接手。

**命中顿帧卡顿**：Tween 受 `time_scale` 影响，标称 0.05s 的顿帧实际走 0.33s；喷焰 T4 每秒触发 91 次。现已限频（命中 90ms / 击杀更短）并 `set_ignore_time_scale(true)`。实测：单次顿帧真实耗时 **28ms**（应接近 30ms）；**连续 20 次命中只触发 0 次顿帧**（限频生效）。

**敌人血条黑线**：底衬不随血量缩短、满宽常驻，已整条移除。实测 `HpBar` 下只有 1 个子节点。

### 6.2 敌我弹道可辨性（`tests/bullet_faction.gd` 15 项 + `bullet_order.gd` 9 项）

全部通过。玩家暖黄 `(1.0, 0.82, 0.35)`，敌人品红 `(1.0, 0.28, 0.68)`，**色相方向相反**；亮度 0.82 vs 0.46。玩家弹丸实体宽度 6px、敌人 6px（散射图案会是 18~20px，枪械图 14px 以上）。tier 由尺寸（1.80/2.02/2.27/2.56）+ 亮度表达，T4 染色接近中性白不叠浑。

### 6.3 弹丸视觉「从未生效」的根因

`_sprite` 是普通 `var` 在 `_ready()` 赋值，但 game 侧 `setup()` **早于** `add_child()`，所有 `if _sprite != null` 分支静默跳过 —— 敌我都是 `bullet_player.png` + 纯白。改为 `_pending_*` + `_ready()` 落地后修复。

**测试曾经骗过自己**：`bullet_faction` 早先因为调用顺序写反（先 `add_child` 再 `setup`）而掩盖了这个真 bug。现已严格复刻 game 侧顺序。

### 7.1 导出模板为什么 1.19 GB

`.tpz` 是**全平台打包**：Windows/Linux/macOS/Android/iOS/Web/visionOS × 多架构 × debug/release。实测构成：

| | 大小 |
|---|---|
| 安卓 + iOS + macOS 中间件 | 512 MB |
| Windows 全部（3 架构 × debug+release） | 589 MB |
| Linux + Web | 329 MB |
| **实际需要的**（`windows_release_x86_64.exe` + `icudt_godot.dat`） | **104.4 MB（占 8.7%）** |

编辑器的「Install Selected Templates」虽然可勾选平台，但**仍下载整个 TPZ**（按平台拆分是 godotengine/godot-proposals#647，至今未实现）。所以一次性下载绕不开，但装的时候可以只解压需要的 —— 磁盘占用从约 2 GB 降到 104.4 MB。

实测下载速度：官方直连 **14 KB/s**（需约 23 小时），走 `gh-proxy.com` 镜像 **27 秒**（约 44 MB/s）。

### 7.2 两处文档/直觉与源码不符

拉 Godot 4.6 源码核对而非依赖文档，发现：

| 选项 | 文档/直觉 | 源码实测默认 | 本工程设为 |
|---|---|---|---|
| `binary_format/embed_pck` | 文档称默认开 | **`false`** | `true`（要单 exe） |
| `application/icon_interpolation` | 未注意 | **Lanczos(4)** | `0` Nearest（像素图标必须） |

另外 `application/modify_resources` 在 4.6 已**内置生效**，不需要外部 `rcedit`。

### 7.3 导出前必修：JSON 加载

Godot 4 起 JSON 被当作资源（godotengine/godot#65295），而本工程 `data/*.json` **没有 `.import` 文件**。若走资源管线被打包成 `.res`，`FileAccess.open("res://data/*.json")` 返回 `null` → 升级池 / 武器表 / 波次表全空、游戏卡死。

编辑器里两种方式都能读通，**只有导出后才能区分**。已收敛为 `RunState.read_json()`：先 `FileAccess` 后 `ResourceLoader`，两种打包行为下都能工作（4 处直读统一）。

## 9. 性能压测（`tests/stress_test.gd`）

对应 `PLAT-003`（60fps、同屏 ≤40 单位、弹幕 ≤300 发）。

```bash
# 必须窗口化：headless 没有渲染，测出来的是空跑
# 脚本自己关垂直同步 + 解除帧率上限，按原始墙钟间隔采样
Godot_v4.6.2-stable_win64_console.exe --path . --resolution 1920x1080 \
  res://tests/stress_test.tscn -- --units=40 --bullets=300 --frames=900
```

口径：关垂直同步后采**原始墙钟帧间隔**（不是 `delta`，那是平滑过的）；排除预热帧（着色器编译 / 资源首次光栅化）；每档跑多次取稳定值。判定：p99 ≥ 55fps 且超预算帧 ≤ 1%。

### 9.1 实测（规格上限档，单屏竞技场）

GTX 1650，`gl_compatibility`，1920×1080。40 单位 + 300 发玩家弹幕，**全场弹幕峰值 372**（敌人自己也在开火）：

| 指标 | 实测 | 预算 |
|---|---|---|
| 平均帧时间 | **3.46 ms**（289.2 fps） | 16.67 ms |
| p50 / p95 / p99 / p99.9 | 2.96 / 6.52 / 8.10 / 9.72 ms | — |
| **超 16.67ms 预算帧占比** | **0.00%** | ≤ 1% |
| p99 最差 FPS | 123.5 | ≥ 55 |
| 物理单核占用 | **31%** | ≤ 100% |
| 绘制调用 | 76 | — |

**`PLAT-003` 达标，余量约 4.8 倍。** 注意「全场弹幕峰值 372」高于策划案的 300 —— 压测只定额维持 300 发玩家弹幕，敌人还会开火（+72），即**达标数据是超规格取得的**，口径偏保守。

产物：`docs/screenshots/stress-specmax.png`（满负载截图）、`user://stress_report.json`（原始数据）。

### 9.2 瓶颈是物理，不是渲染

绘制调用 76，绝对值极小 —— GL Compatibility 把同贴图的 2D 精灵合批了，300+ 弹幕并没有变成 300 次绘制。真正的成本在物理：单核占用 31%。Godot 2D 物理是单线程的，单核到 100% 就撞墙，所以设计上限约在**规格的 3 倍**（约 120 个同屏单位），而非渲染上限。

### 9.3 修掉的一处静默假绿

压测脚本原先取 `_game.get("room")`，但 `game.gd` 的成员在竞技场重写时已改名 `arena`。取到 `null` 后调 `interior_rect()` 报错中断，**脚本却仍以退出码 0 结束** —— 一个「什么都没测却显示通过」的静默失败，而 `PLAT-003` 的性能结论就靠它产出。

已修正取值并加硬失败（取不到 `arena` 直接 `quit(2)`）。修正后实测区域 `(832.0, 464.0)`、41 个单位，确认负载真的搭起来了。

### 9.4 测这个时踩到的坑（都是测量方法本身骗人）

1. **垂直同步**：开着 vsync 测出来永远是 16.67ms，看起来「刚好 60fps」，实际毫无信息量。脚本必须自己关掉。
2. **`get_tree().quit()` 不会立刻停掉 `_process`**：导致 `_report()` 跑两次，第二次样本混进自己截图的 ~99ms 卡顿。加 `_reported` 上锁才干净。
3. **截图放在采样窗口内**：`save_png` 阻塞近 100ms，会凭空造出尾延迟尖刺。挪到采样结束后再截。
4. **`Performance.TIME_PROCESS` 在这个构建里不可信**：实测在 1.78ms 的帧里报出 77ms。物理步 `TIME_PHYSICS_PROCESS` 才单调可信。
5. **CPU 分解不能取报告时刻的瞬时值**（那一帧已被截图和退出卡顿污染），必须在采样窗口内逐帧累计。

### 9.5 顺手修掉的 HUD 问题

满负载截图里右下角闪避冷却条是**血条的红色**：满格表示「闪避可用」，但红色读起来像「正在掉血」。已给 DashBar 单独的青色填充。这类问题只有看图才能发现。

## 10. 字体常驻内存（`tests/font_cost.gd`）

对应策划案「字体 9.8MB 是否值得换成精简子集」。

```bash
# 有字体：渲染工程里实际出现的全部汉字
Godot_v4.6.2-stable_win64_console.exe --path . --resolution 1280x720 \
  res://tests/font_cost.tscn -- --font=on

# 无字体对照组：临时把 project.godot 的 gui/theme/custom 置空（用 tools/theme_ab.py）
python tools/theme_ab.py off
Godot_v4.6.2-stable_win64_console.exe --path . --resolution 1280x720 \
  res://tests/font_cost.tscn -- --font=off
```

### 10.1 实测结果

字库文件合计 **9.58 MB**（`ark-pixel-12px-proportional-zh_hans.ttf` 4.80 MB + `-latin.ttf` 4.78 MB）。工程实际用到 **876 个汉字**。

无字体 / 有字体交错各跑两次，抵消机器状态漂移（1280×720，进程工作集平台值）：

| 组 | 两次采样 | 均值 |
|---|---|---|
| 无全局主题（不加载字体） | 127.3 / 128.1 MB | **127.7 MB** |
| 有全局主题（加载字体） | 132.6 / 132.8 MB | **132.7 MB** |
| **字体净成本** | | **5.0 MB** |

**9.58 MB 的 TTF 实际只带来约 5.0 MB 常驻。** 仓库里占大头的体积是磁盘占用，不是运行时常驻。

字形缓存按需光栅化：把字形集从 876 灌到 **18,000 个汉字**，平台值 131.9 MB —— 相对 876 字形**没有可测增长**（在测量噪声内）。这说明字形缓存的边际成本极低，**不值得为省内存做字体子集化**。

> ⚠️ 上述「5.0 MB」是**修正后**的数字。最初测出 -0.1 MB（等于零），与直觉矛盾，追查发现对照组根本没生效：A/B 脚本的目标串写成 `gui/theme/custom="..."`，而 `project.godot` 里的实际行是 `theme/custom="..."`（**没有 `gui/` 前缀**，它在 `[gui]` 段下），替换命中 0 次 → 两组都加载了字体 → 差值自然趋近 0。现已把切换逻辑挪进 `tools/theme_ab.py`，**写完立即回读自检**，不匹配就报错退出而不是静默取数。教训：**对照实验必须验证对照组真的生效，否则你测的是自己造的假象。**

### 10.2 为什么只能从 OS 视角测

实测把 9.58 MB 字体加载进来，Godot 内部 `MEMORY_STATIC` 几乎不动、字形缓存页数**恒为 0** —— 引擎的内部计数没有如实反映字体开销。headless 下探针显示字体 RID 已建立（支持 24869 字形），但静态内存读数同样不反映。所以只能按进程工作集测。

**按 `$process.Id` 采工作集是错的**：`Godot_*_console.exe` 只是约 5MB 的启动器壳，真正的引擎是另一个进程，按 Id 采会得到恒定假数据。必须按进程名 `Godot*` 汇总。

### 10.3 一个自己造出来的假数据

第一版测「18,000 字形零成本」时用 `substr(0, i+400)` 分批喂字形，新增的字都排在 Label 文本末尾、**落在可视矩形外被裁剪**，根本没进字形缓存。改成滑动窗口 `substr(pos, 400)`、步长 200 让字形落在可视区内，才得到有效数字。
